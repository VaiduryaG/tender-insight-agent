# 面试导向复习资料：LangGraph 在招投标分析 Agent 中的应用

> 全部内容基于项目真实代码（`src/agent/graph_agent.py`、`tests/test_stage4b_langgraph.py`），节点名、字段名、数字都能和代码对上。每节先给"大白话"，再给"面试要点"。

---

## 一、大白话逻辑：我的 LangGraph 是怎么编排的

### 一句话版本

我用 LangGraph 的 `StateGraph` 搭了一个 ReAct Agent，图上有 **3 个节点**、**1 个条件边**，跑的是"模型推理 → 执行工具 → 回到推理"的循环，中间插了一条**幻觉防御**的特殊通道。

### 图长什么样（我代码里的真实结构）

```
START → agent ──（条件边 route_after_agent）──┬─ "tools" → 执行工具 ──→ 回到 agent
                                              ├─ "nudge" → 注入纠正消息 → 回到 agent
                                              └─ END → 正常结束
```

**三个节点，各说人话：**

| 节点名 | 干什么 | 大白话 |
|--------|--------|--------|
| `agent` | 调 LLM 推理，产出 AI 回复（可能附带"我想调某个工具"的请求） | 决策者 |
| `tools` | 用 LangGraph 官方的 `ToolNode` 批量执行模型要调的工具，把结果包成 ToolMessage 塞回对话 | 干活的 |
| `nudge` | 往对话里追加一条纠正消息（提示词常量 `SIMULATED_ANSWER_NUDGE`），要求模型用真数据重新回答 | 纠错员 |

**State（`AgentState`）里放了 3 个字段：**

| 字段 | 类型 | 作用 |
|------|------|------|
| `messages` | `Annotated[list, add_messages]` | 对话主体。`add_messages` 是 LangGraph 的归并函数（reducer）：每个节点返回新消息时是**追加**而不是覆盖，对话历史才能越滚越长 |
| `used_tools` | bool | 本次运行**是否真正调用过工具**。只有 `tools` 节点会把它置 True——这是幻觉防御的判据 |
| `retried` | bool | 是否已经触发过纠正重试。保证 nudge 通道**只走一次**，防止"纠正→再模拟→再纠正"的死循环 |

**流转逻辑：不是线性的，带条件边。** 关键在 `route_after_agent` 这个路由函数——每次 agent 节点跑完，它读 State 里最后一条消息做三岔口判断：

1. 消息里带 `tool_calls`（模型要调工具）→ 走 `tools`
2. 没带 tool_calls（模型给出了最终回答），**但**回答文本带"模拟工具执行"的特征（正则 `looks_simulated` 检测 `Thought:/Action:/Observation:` 这些词），**且** `used_tools` 是 False（全程没真调过工具），**且** `retried` 是 False（还没重试过）→ 走 `nudge`
3. 其余情况 → `END`

### 为什么会有 nudge 这条特殊通道（项目真实踩坑）

我用的模型是智谱 GLM-4-Flash（免费小模型），它有个真实毛病：**不真正发起工具调用，而是在回答文本里"表演"调工具**——输出"Thought: 我调用了查询… Observation: 华为中标 1.2 亿…"，数据全是编的。手写 for 循环的时候，这个防御是循环外面"事后补救"的补丁；迁移到 LangGraph 后，我把它做成了图上一个**一等公民节点 + 条件边**，控制流一目了然，这也是我选 LangGraph 的直接动因（见下一节）。

## 二、对比优势：为什么用 LangGraph 而不是传统 ReAct 循环

### 面试要点（按真实情况排序，前两条是本项目的一手理由）

**1. 定制控制流 express 成图更自然（本项目最强理由）**

传统 ReAct 循环的控制流是焊死的："有 tool_calls 就执行，没有就结束"。我的场景多了一个**幻觉防御分支**——检测到模型编造工具输出时要注入纠正消息重跑。用 for 循环写，这是塞在循环外的补丁；用 LangGraph，就是一个 `nudge` 节点加一条条件边，图上一眼看清。顺带说一句：LangGraph 官方预置的 `create_react_agent()` 也插不进这个自定义分支，所以我是用 `StateGraph` 手搭的图——**没用一行流，是因为需要定制**。

**2. 状态显式化，逻辑可控可测**

传统 ReAct 循环的"状态"就是一个局部 messages 列表，靠闭包在循环里传来传去。LangGraph 把状态定义成 `AgentState` 类：`messages` 怎么合并（`add_messages` 追加语义）、`used_tools`/`retried` 两个控制位谁来写谁读，全是**显式声明**的。判断逻辑（条件边）是纯函数，输入 State 输出边名，可以脱离整个流程单独测——我的 9 个图版测试就是这么写的。

**3. 循环上限语义更清晰**

手写循环用 `max_steps` 数"模型推理了几轮"；LangGraph 用 `recursion_limit` 数"图节点执行了几次"。我代码里做了一次换算：`max_steps * 2 + 6`——因为一轮工具循环要消耗 agent + tools 两个节点，6 是 nudge 重试路径的余量。**这个换算本身说明：图视角逼着你把控制流预算算清楚**，这是它"更可控"的微观体现。

**4. 通用答法（面试官想要的标准答案，可以放前面说）**

ReAct 是"Thinking-Acting-Observing"的固定循环，链条一长模型容易迷失目标、陷入重复调用；LangGraph 用图 + 显式状态管理来编排，节点职责单一、转移条件显式，支持条件分支、循环上限、中断恢复，复杂工作流不会失控。

### 加分故事线（真实且独特）

> "这个项目我先手写了一个 ReAct 循环，跑通后踩了小模型幻觉模拟工具的坑；迁移到 LangGraph 的动机就是把防御逻辑从循环补丁升级成图上的条件边——所以我对'什么时候该上框架'的体会很具体：流程里出现**定制分支**和**多个状态位**的时候。"

## 三、一分钟面试话术（可直接背）

> "这个项目里我用 LangGraph 的 StateGraph 搭了一个招投标分析的 ReAct Agent。图上一共三个节点：agent 节点负责调大模型做推理，tools 节点用 LangGraph 的 ToolNode 批量执行工具——我接了五个工具，比如公司画像、图谱竞对查询、语义搜索；还有一个 nudge 节点，是专门做幻觉防御的。State 里有三个字段：messages 用 add_messages 这个 reducer 做追加式合并；还有两个控制位 used_tools 和 retried，记录'是否真调过工具'和'是否已重试过'。
>
> 整个流转是带条件边的：agent 每次跑完，路由函数读 State 里最后一条消息，带 tool_calls 就进 tools 节点执行再回到 agent；不带就判断是不是'编造工具输出'——因为我用的免费小模型会在文本里假装调工具、数据全是编的。检测到这种模拟，而且确实没调过工具、也没重试过，就走 nudge 节点注入纠正消息，让它基于真实数据重新回答。
>
> 迁移动因是我之前手写过 ReAct 循环，防御逻辑是循环外的补丁，改成 LangGraph 之后定制分支变成了图上的显式节点，控制流一目了然，而且条件边是纯函数，可以脱离整个流程单独写测试——我用脚本化的假 LLM 写了九个用例，零 API 消耗验证了全部路径。"

（约 330 字，正常语速 55-70 秒。面试前掐表练两遍。）

## 四、防穿帮底线

### 问："你是自己手写的底层代码吗？"

**建议回答（坦诚 + 体面 + 把落点放在你真正做的事上）：**

> "底层样板代码我是 AI 辅助生成、再逐行调试的——但我对它是可解释、可改造的，不是黑盒拿过来就用。我自己负责的部分有三块：
>
> 一是**业务节点拆分和图的编排设计**——为什么是三个节点、nudge 这条防御通道怎么插进图里，这是我自己定的架构；二是**状态字段设计**——State 里 `used_tools` 和 `retried` 这两个控制位是我设计的，用来支撑条件边的判断和防死循环；三是**闭环验证**——我用脚本化的 FakeLLM 写了覆盖全部路径的测试，包括幻觉防御触发、调用过工具不误伤、只重试一次这些边界，31 个用例全过。
>
> 举一个我能说明白的细节：LangGraph 的 recursion_limit 数的是**节点执行次数**不是模型轮次，所以我的换算是 max_steps 乘 2 加余量——这个坑是我调试时踩过才明白的。"

### 为什么这样说安全

- **真实**：项目本来就是 AI 协助开发 + 人工设计验证的模式，这么说没有谎言风险；
- **2026 年的面试语境**：AI 辅助编码是常态，面试官真正想筛掉的是"复制粘贴说不出所以然"的人，主动交代 + 展示可解释深度反而是加分项；
- **落点对**：架构决策、状态设计、验证闭环——这些恰恰是 AI 替代不了的，也是你确实做了的。

### 追问弹药（背下来，每条 15 秒内能答）

| 可能的追问 | 答法（要点） |
|-----------|-------------|
| "add_messages 是干嘛的？" | State 里 messages 字段的归并函数（reducer）。节点返回新消息时默认会覆盖整个列表，加了它才是追加——对话历史才能累积。 |
| "条件边怎么写的？" | `add_conditional_edges("agent", route_after_agent, {边名: 目标})`。路由函数读 State 返回字符串边名，映射表决定跳到哪个节点，是纯函数可单测。 |
| "为什么不用 create_react_agent 一行流？" | 预置的只有"有 tool_calls 走 tools、没有就结束"这条固定路径，我的幻觉防御要插第三个分支，插不进去，所以用 StateGraph 手搭。 |
| "ToolNode 怎么接到你自己的工具上的？" | 我写了个适配层，把自研 ToolRegistry 里的工具包装成 LangChain 的 BaseTool：参数 schema 从 JSON Schema 动态生成 pydantic 模型，执行还是委托回原来的 registry——工具逻辑一处维护，两版 Agent 共用。 |
| "测试怎么做的不花 API 钱？" | 脚本化替身 FakeLLM：按预设顺序返回"先调工具→再给回答"的消息序列，喂给 Agent 跑完整图流程，再断言最终回答、trace、重试标记。 |
| "遇到过什么坑？" | 两个：① langchain 消息的 role 是 human/ai，直接透传给智谱 API 会报 400"角色信息不正确"（错误码 1214），必须显式映射成 user/assistant；② recursion_limit 的单位是节点次数不是模型轮次，我按 agent+tools 一轮两个节点做了换算。 |

### 最后三道保险

1. **跑一遍测试**再进面试：`./run.sh -m pytest tests/test_stage4b_langgraph.py -v`——亲手看到 9 个 passed，底气不一样；
2. **能画出那张三节点一条件边的图**——面试官让你画图时，这比任何背诵都有说服力；
3. **守住诚实边界**：只讲你能画出来、能改得动的部分；被问到没准备过的（比如 checkpointer 持久化、断点恢复），直接说"这块我当前版本没用到，计划里是下一步"——不知道不丢人，编才穿帮。

## 附：一句话速记卡

- **图结构**：START → agent →（条件边）→ tools / nudge / END；tools 和 nudge 都回 agent
- **节点**：agent（推理）、tools（ToolNode 执行）、nudge（注入 `SIMULATED_ANSWER_NUDGE` 纠错）
- **State**：`messages`（add_messages 追加）+ `used_tools` + `retried`
- **条件边**：`route_after_agent` 三岔口——有 tool_calls→tools；模拟特征+没真调过+没重试过→nudge；否则 END
- **换算**：`recursion_limit = max_steps * 2 + 6`（节点次数 ≠ 模型轮次）
- **验证**：FakeLLM 零 API 消耗，图版 9 用例 + 手写版 22 用例 = 31 passed
